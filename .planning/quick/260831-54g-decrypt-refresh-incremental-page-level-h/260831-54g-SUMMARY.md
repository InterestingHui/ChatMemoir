# 260831-54g: Decrypt refresh incremental at page level

Routine GUI refresh re-AES'd ~1GB to capture ~0.3% of changed pages; now a
page-level HMAC-tail diff skips unchanged pages entirely, and a per-file key
cache removes the ~15s of PBKDF2 per refresh. Steady-state refresh = seconds.

## What was done

**Task 1 — `memoir/decrypt/decrypt_v4.py`** (d1ed605)
- New module-private `_sync_pages_incremental(pkey, in, out)`: compares each
  page's 80B IV+HMAC tail between src ciphertext and the existing decrypted
  output (tails are copied verbatim by the decrypt layout, so tail-equal =
  ciphertext-unchanged); rewrites only changed/appended pages in place
  (`r+b`, seek+write).
- Tri-state: `True` synced / `False` key error (HMAC mismatch → return
  immediately, dst NOT deleted — it still holds the previous consistent
  snapshot) / `None` preconditions unmet (dst missing/sub-page/misaligned,
  or src smaller than dst).
- `decrypt_db_file_v4` calls the helper after the existing chmod; on `None`
  or ANY exception falls through to the unchanged full `'wb'` body (wipes
  half-synced state, keeps finally-remove semantics). `False` returns before
  the full path's try/finally so dst survives.
- Sequential src reads only (9p-safe); no-op sync skips truncate so mtime
  stays untouched; zero-page and page-0 SQLite-header handling identical to
  the full path. `decrypt_db_files` / `decode_wrapper` untouched.

**Task 2 — `gui/decryption.py`** (50f3dea)
- `_try_passphrase_decrypt_refresh` step 4: two-pass key derivation over
  `decrypted/<uid>/keycache.json` (`{rel_path: {"salt", "key"}}`). Pass A
  reads each file's 16B salt and serves hits from cache; Pass B PBKDF2s only
  the misses with progress denominator = len(misses). Merged cache written
  back unpruned. Cache is only consulted after step-3 passphrase
  verification, so cached keys are guaranteed same-passphrase; salt match is
  the validity check.
- `_fresh_snapshot_dir` gate 30min → 10min (docstring + knob comment updated).

**Task 3 — `tests/test_incremental_decrypt.py`** (5ebabf5, committed first
per TDD; check-5 assert fix in d1ed605)
- Standalone (no pytest, sys.path insert, tempfile only). `build_src` writes
  synthetic WCDB v4 files in the exact production format (salt/IV/HMAC per
  page, one all-zero page) and returns expected plaintext pages.
- 5 checks: (1) full-decrypt semantics + tail invariant, (2) incremental ==
  full across 2 in-place rewrites + 3 appends, (3) no-op sync leaves content
  hash and mtime_ns unchanged, (4) corrupted HMAC → returns False with dst
  bytes intact, (5) shrunk src → full rewrite == fresh full decrypt.

## Orchestrator verification (post-executor)

Real-data smoke on live ttlo `message_6.db` (342MB, hardest case: 308 in-place
rewrites + appends), run against /tmp copies to protect the real snapshot:

- First live-run showed inc != full + malformed → diagnosed as **live-write
  tearing** (WeChat wrote ~50 pages during the runs; both outputs captured
  different time points), NOT a sync bug — proven by the frozen-src control:
  same frozen src through incremental vs full = **byte-identical**, integrity
  ok on both. Tearing is pre-existing (old full path reads live files too);
  the faster reads shrink the window ~5x. Not fixed here.
- Bottleneck found during smoke: page-at-a-time reads through the default 8KB
  buffer run ~10MB/s on 9p → **5c2326e**: 1MB buffering on src read (both
  paths) + full-path write. Live 342MB: full 34.5s → 7.0s, incremental
  24.2s → 5.8s; frozen inc 1.4s vs full 4.2s, identical bytes.
- Suite re-run after buffering change: 5/5 PASS.
- End-to-end estimate for the user's 29-file corpus on a typical day
  (~1GB changed): ~15-20s total refresh (was ~15s PBKDF2 + minutes of AES).
