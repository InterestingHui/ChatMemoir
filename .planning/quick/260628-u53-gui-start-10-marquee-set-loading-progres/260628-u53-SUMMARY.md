# Quick Task 260628-u53: Fix GUI decryption progress bar marquee-mode mismatch

Fixed the GUI decryption progress bar so it transitions from marquee (auto-scroll) mode to determinate mode the first time real decryption progress arrives, instead of silently ignoring every `progress_callback` update.

## Root Cause

`gui/decryption.py:_on_start` enters marquee mode via `self._loading_progress.start(10)` to give the user something moving during the scan/YARA phase. `ttk.Progressbar` in marquee mode **silently ignores** writes to its `["value"]` attribute until `stop()` is invoked. The original `LoggingMixin.set_loading_progress` only set `["value"]`, so the very first `progress_callback=self.set_loading_progress` call from `decrypt_v4.decrypt_db_files` (and every one after it) was dropped on the floor. Users saw an endless scrolling bar disconnected from the actual decryption work.

## Fix

Inside the `_update` closure of `set_loading_progress` (gui/logging.py), call `self._loading_progress.stop()` **before** setting `["value"]`. Wrapped in `try/except Exception: pass` so:
- On a real `ttk.Progressbar`, `stop()` is a documented no-op when not in marquee mode (idempotent).
- On mock/test backends (or any backend lacking `stop()`), the swallowed `AttributeError` cannot break the value update.

`gui/decryption.py` is intentionally unchanged — `start(10)` is preserved so marquee feedback during the scan phase is unchanged; the fix only transitions the bar out of marquee the first time real progress arrives.
