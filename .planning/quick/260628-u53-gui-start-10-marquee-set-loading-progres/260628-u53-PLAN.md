Output: Patched `gui/logging.py:set_loading_progress` that calls `_loading_progress.stop()` before setting `["value"]`, plus a regression unit test.

```python
class LoggingMixin:
    def log(self, msg, loading=True): ...
    def set_loading_status(self, text): ...
    def set_status(self, msg): ...
    def set_loading_progress(self, current, total, filename=""): ...  # <-- the method being fixed
    def set_progress(self, pct): ...
```

Caller wiring (gui/decryption.py):
- `_on_start` (line 14) calls `self._loading_progress.start(10)` (line 17) → enters marquee mode for the scan phase.
- `_auto_decrypt` passes `progress_callback=self.set_loading_progress` to `decrypt_v4.decrypt_db_files` (line 160) and seeds `self.set_loading_progress(0, 1, "")` (line 146) before decryption begins.
- `_on_decrypt_done` / `_on_decrypt_error` already call `self._loading_progress.stop()` — they are NOT the problem.

Root cause: ttk.Progressbar in marquee mode (started via `start([intervalMs])`) ignores `["value"]` writes until `stop()` is called. The current `set_loading_progress` only sets `["value"]`, so the first real progress update (and all subsequent ones) are silently dropped.

Fix: Inside `set_loading_progress`'s `_update` closure, call `self._loading_progress.stop()` before setting `["value"]`. `stop()` is idempotent — a no-op when not in marquee mode — so it is safe to call on every update.
