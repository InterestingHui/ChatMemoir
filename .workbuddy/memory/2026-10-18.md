# 2026-10-18

## GUI 启动解密卡顿修复（卡在 media_1.db / 大库假死）
- 现象：GUI 打开走 WSL 本地增量解密路径，key 全缓存命中，但卡在「正在解密 xx 的当前数据...」约 97s 无进度更新，像假死。
- 根因（今晚日志 2026-10-18-log.log 实测）：
  1. `_sync_pages_incremental` 对 dst 每页做 seek+read(4KB) 比对尾巴，29.6 万页的 message_0.db 单库 42.5s（9p 上 4KB 随机读只有 ~18MB/s，1MB 顺序读 ~131MB/s）。
  2. 微信在线时活跃库（message_6/fts/session 等）每 ~2-3 分钟被 checkpoint 摸一次 mtime，每轮 GUI 刷新都要整库页级扫描。
- 修复（memoir/decrypt/decrypt_v4.py，+68/-8）：
  1. dst 比对改为顺序 1MB 大块读 + 内存切页（f_dst 只读流 + f_out r+b 只写变更页）。页级同步 42.5s/库 → ~3s/库。
  2. 新增 sync_manifest.json（decrypted/<uid>/ 下，仅 /mnt/c 9p 源启用）：src (size, mtime_ns) 与上次成功同步一致 → 直接跳过页级扫描。稳态全短路轮 <1s。
- 踩坑记录：
  - 写清单签名不能用 `int(st_mtime*1e9)`（浮点秒×1e9 在 9p 上精度丢失，末几位不稳定 → 清单永不命中），必须直接 `st.st_mtime_ns`。
  - 解密期间被微信写入的库（before != after，撕裂读重试路径）不记清单——快照已落后，记了也白记。
  - `decrypt_db_files` 全跳过时返回 (skipped=29, 0)，调用方靠 failed 判定，语义没破。
- 验证：三连跑收敛 5→0.92s→0.90s；端到端 GUI 路径（DecryptionMixin._try_passphrase_decrypt_refresh）首刷 9.4s、稳态 0.34s（新鲜度门短路）；解密产物 sqlite 完整性抽查通过（message_0.db 3222 tables）。
- 遗留观察：微信活跃写的库每轮仍会走页级同步（几秒级），这是正确性优先的预期行为；真正卡死的 97s 已消除。
